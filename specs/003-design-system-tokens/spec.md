# Feature Specification: デザインシステム準拠のデザイントークン整備と全画面適用

**Feature Branch**: `003-design-system-tokens`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "デザインをリファクタします。デザインシステムにデジタル庁のデザインシステムを踏襲したものにしたいと考えています。現在の見た目がのっぺりしているので"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 画面内の情報の階層がひと目で分かる (Priority: P1)

利用者が各画面を開いたとき、見出し・本文・補足という役割の違いがひと目で区別でき、
どこからどこまでが1つの情報のまとまりなのかが視覚的に分かる。

**Why this priority**: 「のっぺりしている」という現状の不満そのものを解消する中心的な価値であり、
これが達成されなければ本フィーチャーの目的が満たされない。

**Independent Test**: 4画面を順に開き、各画面で「見出し」「本文」「補足」の3つの役割が
視覚的に区別できること、および情報のまとまりの境界が識別できることを確認する。

**Acceptance Scenarios**:

1. **Given** いずれかの画面を開いている, **When** 画面を見る, **Then** 見出し・本文・補足が文字サイズ・太さ・色の複数の差によって区別できる `[手動]`
2. **Given** いずれかの画面を開いている, **When** 画面を見る, **Then** 情報のまとまりが面(カード・境界線・elevation)として認識でき、どこで区切られているかが分かる `[手動]`
3. **Given** 記録が0件の空状態、または読み込み中の状態, **When** 画面を見る, **Then** 通常表示時と同じ階層表現が保たれており、平坦な見た目にならない `[手動]`

---

### User Story 2 - 入力領域と結果表示領域が視覚的に分離される (Priority: P2)

利用者が記録の入力フォームと、記録された結果の表示領域を、面の区切りによって明確に区別できる。

**Why this priority**: 現状は入力と結果が同じ平面に並んでいるため操作対象を見失いやすい。
P1の階層表現と独立して検証・提供できる価値である。

**Independent Test**: 記録画面(体重・トレーニング・歩数)を開き、入力フォームと結果表示が
別の面として区別できることを確認する。

**Acceptance Scenarios**:

1. **Given** 体重・トレーニング・歩数のいずれかの記録画面を開いている, **When** 画面を見る, **Then** 入力フォームの領域と結果表示の領域が別の面として区別できる `[手動]`
2. **Given** 入力フォームで検証エラーが表示されている, **When** 画面を見る, **Then** エラーの表示が該当フィールドと同じ面の中で結び付いて認識できる `[手動]`

---

### User Story 3 - デザインの変更が定義1箇所で完結する (Priority: P3)

開発者が色・タイポグラフィ・余白などを変更したいとき、トークン定義1箇所を修正すれば
全画面に反映される。新しいコンポーネントを追加するときも、参照すべきトークンが定義済みで、
生の値を書かずに実装できる。

**Why this priority**: 見た目の一貫性を将来にわたって保つための土台だが、
利用者が直接目にする価値ではないためP1・P2の後に置く。

**Independent Test**: トークン定義の値(例: 基準となる余白量)を1箇所変更し、
全画面の表示が連動して変わることを確認する。

**Acceptance Scenarios**:

1. **Given** トークンが一元的に定義されている, **When** 定義中の値を1箇所変更する, **Then** その値を使うすべての画面に変更が反映される `[自動]`
2. **Given** 対象コンポーネントのソースを検査する, **When** 色コードや寸法の直接指定を探す, **Then** トークンを迂回した直接指定が存在しない `[自動]`

---

### User Story 4 - 全画面・全コンポーネントで見た目が一貫している (Priority: P4)

利用者が画面を移動しても、余白の取り方・文字サイズ・配色・角の丸みが画面ごとにばらつかず、
同じ規則で構成されていると感じられる。

**Why this priority**: 一貫性は品質として重要だが、個々の画面の階層表現(P1)が
成立した後に評価される性質のため最後に置く。

**Independent Test**: 4画面とアプリシェルを順に巡回し、同じ役割の要素が画面をまたいで
同じ見え方をしていることを確認する。

**Acceptance Scenarios**:

1. **Given** 4つの画面すべてが適用済みである, **When** 画面を順に移動する, **Then** 同じ役割の要素(画面見出し、入力フォーム、一覧、補足文)が画面をまたいで同じ見え方になっている `[手動]`
2. **Given** 共通コンポーネント(空状態・読み込み中・期間切替)を含む画面を開いている, **When** 画面を見る, **Then** 共通コンポーネントも同じ規則の配色・余白・文字サイズで表示される `[手動]`

---

### Edge Cases

- 極端に大きい数値(例: 100,000歩、5桁のカロリー値)が入ったとき、面や表のレイアウトが崩れないか
- 日本語の長いテキスト(食材名、算出根拠の出典表記など)が折り返されたとき、行間・余白の規則が保たれるか
- 画面幅が狭い端末(375px程度のスマートフォン)で、面の入れ子や余白が過剰にならず横スクロールも発生しないか
- 利用者のOS・ブラウザ側で文字サイズが拡大されているとき、レイアウトが破綻しないか
- グラフ表示の配色が、画面全体の配色と乖離して浮いて見えないか
- 記録が0件のとき・読み込み中のときに、面や階層が失われて平坦に見えないか
- 視覚以外の手段(表形式・テキスト要約)でも同等の情報が得られる状態が維持されているか

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、色・タイポグラフィ・余白・角丸・境界線・elevationのデザイントークンを一元的に定義し、すべての画面・コンポーネントがその定義を参照しなければならない。
- **FR-002**: システムは、デザイントークンの値をデジタル庁デザインシステムのデザイン原則・トークン体系に沿って定めなければならない。
- **FR-003**: 対象コンポーネントは、トークンを迂回した生の値(色コード・寸法など)を直接記述してはならない。
- **FR-004**: システムは、見出し・本文・補足の役割をタイポグラフィ(サイズ・太さ・色)の差によって視覚的に区別できるようにしなければならない。
- **FR-005**: システムは、情報のまとまりを面(カード・境界線・elevation)と余白のリズムによって視覚的に示さなければならない。要素が平坦に並ぶだけの表示にしてはならない。
- **FR-006**: システムは、入力フォームの領域と結果表示の領域を、面の区切りによって視覚的に分離しなければならない。
- **FR-007**: システムは、余白を一貫した尺度(スケール)に従って適用しなければならない。画面ごとに恣意的な余白を用いてはならない。
- **FR-008**: システムは、文字と背景のコントラスト比について、通常サイズの文字で4.5:1以上、大きいサイズの文字で3:1以上を満たさなければならない。
- **FR-009**: システムは、既存の自動アクセシビリティ検査の違反を0件に保たなければならない。適用によって新たな違反を発生させてはならない。
- **FR-010**: システムは、視覚以外の手段(表形式・テキスト要約)で同等の情報を取得できる既存の仕組みを維持しなければならない。
- **FR-011**: システムは、画面幅375px以上の環境で横スクロールを発生させずに表示できなければならない。
- **FR-012**: システムは、日本語テキストの本文で、可読性に足る行間を確保しなければならない。
- **FR-013**: システムは、本フィーチャーによって機能・データモデル・APIスキーマ・ドメインロジックを変更してはならない。変更対象は視覚表現に限る。
- **FR-014**: システムは、本文および見出しに、デジタル庁デザインシステムが指定する日本語書体を用いなければならない。書体の読み込みが完了していない間も本文が読める状態を保ち(代替書体での先行表示)、読み込み完了時に表示が大きく崩れてはならない。
- **FR-015**: システムは、明るい配色モードのみを提供する。暗い配色モード(ダークモード)への対応は本フィーチャーの対象外とし、将来の別フィーチャーとして扱う。
- **FR-016**: システムは、画面間の移動手段を、デジタル庁デザインシステムの流儀に沿った画面上部の領域(ヘッダー)とナビゲーションとして提供しなければならない。現在地の画面が視覚的に判別でき、かつキーボードのみで各画面へ移動できなければならない。
- **FR-017**: システムは、デジタル庁デザインシステムの利用条件に従い、必要な帰属表示・出典記載を利用者が確認できる形で含めなければならない。

### Key Entities *(include if feature involves data)*

- **デザイントークン**: 見た目を構成する値の最小単位。色・タイポグラフィ(サイズ・太さ・行間)・余白・角丸・境界線・elevationの各カテゴリを持ち、一元的に定義されて全画面から参照される。
- **視覚的階層**: 見出し・本文・補足という役割の区別と、情報のまとまりの境界。トークンの組み合わせによって表現される。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 4つの画面すべてで、見出し・本文・補足の3階層が視覚的に区別できる。
- **SC-002**: 4つの画面すべてで、情報のまとまりの境界が面として識別できる。
- **SC-003**: 記録画面(体重・トレーニング・歩数)で、入力領域と結果表示領域が別の面として区別できる。
- **SC-004**: トークン定義1箇所の変更が、その値を使うすべての画面に反映される。
- **SC-005**: 対象コンポーネント内に直接記述された色コード・寸法が0件である。
- **SC-006**: 自動アクセシビリティ検査の違反が0件を維持している。
- **SC-007**: 文字と背景のコントラスト比が、通常文字4.5:1・大きい文字3:1の基準を満たしている。
- **SC-008**: 画面幅375pxで、4画面すべてが横スクロールなしに表示できる。
- **SC-009**: 既存の自動テストがすべて引き続き成功し、機能・データに影響が出ていない。
- **SC-010**: 開発者本人が、適用前後を比較して「のっぺりしている」状態が解消されたと判断できる。
- **SC-011**: すべての画面で現在地が視覚的に判別でき、キーボードのみで4画面すべてへ移動できる。
- **SC-012**: 書体の読み込み中も本文が判読でき、読み込み完了時に主要な要素の位置が大きく飛ばない。

## Assumptions

- 利用者は開発者本人のみであり、個人利用という前提は維持する。
- 本フィーチャーは視覚表現の変更に限定し、記録機能・集計ロジック・APIスキーマ・データモデルには手を入れない。
- デザイントークンの値の一次情報はデジタル庁デザインシステムの公開ドキュメントおよび公開デザインデータとし、具体的な参照・取得手段はplanの段階で決定する。
- 適用の進め方(4画面を一括で切り替えるか、画面ごとに段階適用するか)はplan・tasksの段階で決定する。本specは最終的に全画面へ適用されることのみを要件とする。
- グラフ表示の配色も、画面全体と同じトークンの配色に合わせる。
- 既存の自動テストのうち、文言や寸法の期待値が見た目の変更に伴って変わるものは、原則III(テスト先行)に従って先に期待値を更新してから実装する。
- 「のっぺりしている」状態が解消されたかの最終判断は開発者本人の主観評価を含むため、`[手動]`の受け入れ条件として扱う。
- 印刷用スタイル、アニメーション・モーションの体系的な設計は本フィーチャーの対象外とする。

## 決定事項(clarificationの解決結果)

以下3点は仕様策定時の論点として挙がり、本specの確定にあたり決定した。いずれもspecの改訂で変更可能。

- **書体(FR-014)**: デザインシステム指定の日本語書体を配信する。原則X(踏襲する)においてタイポグラフィは中核であり、「のっぺり」解消への寄与も大きいため、端末搭載書体での代替は採らない。配信容量・読み込み待ちへの対処方法はplanで決定する。
- **配色モード(FR-015)**: 明るい配色のみとし、ダークモードは対象外。解決すべき課題は「のっぺり」であり夜間の眩しさではないため、全トークンを2系統に増やす作業量は本フィーチャーの目的に対して見合わない。
- **ナビゲーション(FR-016)**: ヘッダー+ナビゲーションとして作り直す。現在の素朴なテキストリンク並びは平坦な見た目の主要因の一つであり、トークン適用のみでは主目的(SC-010)が未達に終わる可能性が高いため。
