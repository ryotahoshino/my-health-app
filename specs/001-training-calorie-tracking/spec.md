# Feature Specification: 体重・トレーニング記録と消費カロリーの可視化

**Feature Branch**: `001-training-calorie-tracking`

**Created**: 2026-08-16

**Status**: Draft

**Input**: User description: "トレーニングと体重を記録し、消費カロリーとして可視化できるようにしたい。

## 目的
アプリ全体のアーキテクチャ(UI → GraphQL API → 永続化)を確立しつつ、「記録して、消費カロリーとして見える化する」という本アプリの中核価値を実現する。アクセシビリティ対応の実装パターン(フォームのエラー提示、グラフの非視覚的な代替)もここで確立し、以降の機能で再利用する。

## 対象ユーザー
開発者本人のみ。単一ユーザーを前提とし、ログインは行わない。

## ユーザーストーリー(優先度順)
P1: 体重を記録して推移を見る / P2: トレーニングを記録する / P3: トレーニングによる消費カロリーを見る / P4: 歩数による消費カロリーを見る / P5: 食材のカロリーとPFCを参照する

## 決定済みの方針
永続化は差し替え可能な抽象の裏に置く/マルチデバイス対応はレスポンシブで満たす/歩数は手入力のみ/種目マスタは固定データ/消費カロリーの二重計上を避ける/期間集計はプリセット方式(日次・週次・月次)

## 満たしたい観点
キーボード操作、フィールド関連付けエラー、グラフの非視覚的代替、単位・小数点の明示、サーバー・クライアント共通バリデーション

## スコープ外
認証・複数ユーザー対応、摂取カロリー記録、ヘルスケア連携全般、端末間同期、任意日付範囲指定、種目マスタCRUD、本番デプロイ・コンテナ化、食材の摂取記録・栄養計算

## 仕様策定で決めたい論点
永続化の初期実装、週の開始曜日と期間定義、集計タイムゾーン、同日複数回記録の扱い、数値の入力範囲と小数点桁数、記録0件時の画面表示"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 体重を記録して推移を見る (Priority: P1)

開発者が日々の体重を記録し、日付ごとの一覧とグラフで推移を確認する。記録は後から修正・削除できる。

**Why this priority**: 消費カロリーの算出には体重が必要であり、P3・P4の前提となる。一方でこのストーリー単体でも「体重の推移を見える化する」という価値を独立して提供できるため、最初に着手する。

**Independent Test**: 体重記録機能のみを実装した状態で、複数日分の体重を入力・編集・削除し、その結果が一覧とグラフに反映されることを確認することで、他のストーリーに依存せずテストできる。

**Acceptance Scenarios**:

1. **Given** 体重記録が1件もない状態, **When** 日付と体重(kg)を入力して保存する, **Then** 一覧に新しい記録が表示され、グラフにも反映される `[自動]`
2. **Given** 既存の体重記録がある状態, **When** その記録の体重値を変更して保存する, **Then** 一覧とグラフの値が更新される `[自動]`
3. **Given** 既存の体重記録がある状態, **When** その記録を削除する, **Then** 一覧とグラフからその記録が消える `[自動]`
4. **Given** 体重記録が2件以上ある状態, **When** 推移グラフを表示する, **Then** 同じデータを表形式でも取得でき、推移の要約をテキストでも読める `[自動]`
5. **Given** 体重の入力フォームが表示されている状態, **When** マウスを使わずキーボードのみで日付・体重の入力から保存までを行う, **Then** すべての操作が完了できる `[手動]`
6. **Given** 不正な体重値(範囲外・空欄など)を入力した状態, **When** 保存を実行する, **Then** エラーが対象フィールドに関連付けて表示され、原因と直し方が分かる `[自動]`

---

### User Story 2 - トレーニングを記録する (Priority: P2)

開発者が、その日のトレーニング全体をセッションとして記録し、セッションに紐づけて種目・セット数・回数・重量を記録する。

**Why this priority**: 体重記録の次に、トレーニング内容を構造化して記録できることが、P3(トレーニングによる消費カロリー可視化)の前提になる。

**Independent Test**: セッション(日付・実施時間・強度区分)を作成し、そのセッションに種目・セット数・回数・重量を追加して、一覧・詳細に反映されることを確認することで、P1・P3以降に依存せずテストできる。

**Acceptance Scenarios**:

1. **Given** トレーニング記録が1件もない状態, **When** 日付・実施時間(分)・強度区分を入力してセッションを作成する, **Then** セッションが一覧に表示される `[自動]`
2. **Given** 作成済みのセッションがある状態, **When** そのセッションに種目・セット数・回数・重量を追加する, **Then** セッションの詳細にその内容が表示される `[自動]`
3. **Given** セッションに複数の種目が記録されている状態, **When** セッション一覧または詳細を開く, **Then** 記録した種目・セット数・回数・重量がすべて確認できる `[自動]`
4. **Given** 実施時間や強度区分に不正な値を入力した状態, **When** 保存を実行する, **Then** エラーが対象フィールドに関連付けて表示される `[自動]`
5. **Given** セッション入力フォームが表示されている状態, **When** キーボードのみで種目の追加・削除を含む一連の入力を行う, **Then** すべての操作が完了できる `[手動]`

---

### User Story 3 - トレーニングによる消費カロリーを見る (Priority: P3)

開発者が、記録したトレーニングセッションの消費カロリーを確認する。算出根拠(計算式・定数・出典)も画面上で確認できる。

**Why this priority**: P1(体重)とP2(トレーニング記録)の両方を前提として初めて成立する、本アプリの中核価値(記録の消費カロリー可視化)の最初の実現。

**Independent Test**: P1・P2が成立している前提で、実施時間・強度区分・体重が揃ったセッションについて、算出された消費カロリーと計算式・定数・出典が画面に表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 実施時間・強度区分が記録されたセッションと、直近の体重記録がある状態, **When** セッションの詳細を開く, **Then** 消費カロリーの推定値が表示される `[自動]`
2. **Given** 消費カロリーが表示されている状態, **When** その算出根拠を確認する, **Then** 使用したMETs方式の計算式・仮定した定数・出典が画面上で確認できる `[自動]`
3. **Given** セット数・回数・重量が記録されているセッション, **When** セッション詳細を開く, **Then** 総ボリューム(重量×回数×セット)が消費カロリーとは別の指標として表示される `[自動]`
4. **Given** 体重記録が1件もない状態, **When** 消費カロリーの算出が必要なセッション詳細を開く, **Then** 体重未記録により算出できない旨が分かりやすく示される `[自動]`

---

### User Story 4 - 歩数による消費カロリーを見る (Priority: P4)

開発者が、手入力した歩数から消費カロリーを確認する。トレーニングによる消費カロリー(P3)と合算した1日分の消費カロリーも確認できる。

**Why this priority**: P3で確立した消費カロリー可視化の枠組みを歩数にも拡張し、1日単位の消費カロリー像を完成させる。

**Independent Test**: P3が成立している前提で、日付と歩数を入力し、算出された消費カロリーと、その日のトレーニング分との合算値が表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 歩数記録が1件もない日, **When** 日付と歩数を入力して保存する, **Then** その日の歩数による消費カロリーが表示される `[自動]`
2. **Given** 歩数による消費カロリーが表示されている状態, **When** その算出根拠を確認する, **Then** 使用したMETs値・ケイデンス(歩/分)などの定数と出典が画面上で確認できる `[自動]`
3. **Given** 同じ日にトレーニングセッションと歩数記録の両方がある状態, **When** その日の合計消費カロリーを表示する, **Then** トレーニング分と歩数分を合算した値と、概算である旨の注記が表示される `[自動]`
4. **Given** 歩数のみ記録されトレーニング記録がない日, **When** その日の消費カロリーを表示する, **Then** 歩数分のみの値が表示される `[自動]`

---

### User Story 5 - 食材のカロリーとPFCを参照する (Priority: P5)

開発者が、よく食べる食材の100gあたりカロリーとPFCを一覧で参照する。記録機能ではなく参照専用の一覧とする。

**Why this priority**: 他の記録機能に依存しない参照専用機能であり、優先度は最も低いが独立して提供できる。

**Independent Test**: 食材一覧画面を開き、100gあたりのカロリーとPFCが表示されることを確認することで、他のストーリーと独立してテストできる。

**Acceptance Scenarios**:

1. **Given** 食材一覧画面を開く, **When** 一覧を表示する, **Then** よく食べる食材について100gあたりのカロリーとPFC(タンパク質・脂質・炭水化物)が表示される `[自動]`
2. **Given** 食材一覧が表示されている状態, **When** スクリーンリーダーで一覧を読み上げる, **Then** 各食材の名称・カロリー・PFCの対応関係が正しく伝わる `[手動]`

---

### Edge Cases

- 体重・トレーニング・歩数のいずれの記録も0件のとき、一覧・グラフ・集計画面はどう表示されるか(→ 空状態メッセージと記録作成への導線を表示する)
- 集計対象期間(日次・週次・月次)の中に記録がない日が含まれる場合、その日をグラフ・集計上でどう扱うか(0と欠測を区別し、誤解を招く表現を避ける)
- トレーニング中の歩数と歩数記録由来の消費カロリーが重複しうる場合、合算値が概算である旨をどう明示するか
- 消費カロリーの算出に必要な体重記録が存在しない場合、算出不可であることをどう示すか
- 極端に大きい・小さい数値(体重・実施時間・歩数など)が入力された場合、どこまでを許容するか
- 同一日に2回目のトレーニングを記録しようとした場合、新規セッションではなく既存セッションへの上書き(編集)として扱われる(FR-017)。この挙動がUI上で利用者に伝わるようにする

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは日付と体重(kg)を記録・編集・削除できなければならない。
- **FR-002**: システムは体重記録の一覧を日付順に表示しなければならない。
- **FR-003**: システムは体重記録の推移をグラフで表示しなければならない。
- **FR-004**: システムは体重推移グラフと同じデータを表形式でも提供し、推移の要約をテキストでも提供しなければならない。
- **FR-005**: システムはトレーニングセッション(日付・実施時間(分)・強度区分)を記録・編集・削除できなければならない。
- **FR-006**: システムはトレーニングセッションに紐づけて、種目・セット数・回数・重量を記録できなければならない。
- **FR-007**: システムは固定データとして保持する種目マスタ(種目名・METs値・出典)から種目を選択できるようにしなければならない。種目マスタ自体の作成・編集・削除は本機能の対象外とする。
- **FR-008**: システムはトレーニングセッションの実施時間・強度区分・直近の体重からMETs方式で消費カロリーを算出し、表示しなければならない。
- **FR-009**: システムは消費カロリーの算出に用いた計算式・仮定した定数・出典を画面上で確認できるようにしなければならない。
- **FR-010**: システムはセット数・回数・重量から総ボリューム(重量×回数×セット)を算出し、消費カロリーとは別の指標として表示しなければならない。
- **FR-011**: システムは体重記録が存在しない場合、消費カロリーを算出せず、算出できない旨を明示しなければならない。
- **FR-012**: システムは日付と歩数の手入力による記録ができなければならない。ヘルスケアアプリのエクスポートファイル取り込みは対象外とする。
- **FR-013**: システムは歩数からMETs方式で消費カロリーを算出し、使用したMETs値・ケイデンス(歩/分)などの定数と出典を画面上で確認できるようにしなければならない。
- **FR-014**: システムは同一日のトレーニングによる消費カロリーと歩数による消費カロリーを合算した1日分の消費カロリーを表示し、合算値が概算である旨を明示しなければならない。
- **FR-015**: システムはよく食べる食材について、100gあたりのカロリーとPFC(タンパク質・脂質・炭水化物)の一覧を参照専用で提供しなければならない。この一覧に対する記録・編集機能は提供しない。
- **FR-016**: システムは記録データを日次・週次・月次のプリセットで集計・表示できなければならない。任意の期間範囲指定は対象外とする。週は月曜始まりとし、「今週」「今月」は期間開始日から当日までの経過分のみを集計対象とする(未到来の未来日は含めない)。
- **FR-017**: システムは同一日付に対する記録を、体重・歩数・トレーニングセッションのいずれも既存記録への上書きとして扱い、1日につき1件に統一しなければならない。トレーニングセッションを同日に複数回記録しようとした場合も、既存セッションへの上書き(編集)として扱う。
- **FR-018**: すべての入力フォームはキーボードのみで操作でき、フォーカス移動と保存・削除などの実行操作が可能でなければならない。
- **FR-019**: 入力エラーは対象フィールドと関連付けて提示し、何が・なぜ・どう直すべきかが分かる形で示さなければならない。
- **FR-020**: 数値項目は単位と小数点以下の扱いを画面上に明示しなければならない。
- **FR-021**: 入力値のバリデーションルール(範囲・必須・書式)は、クライアントとサーバーで同一の定義から生成されなければならない。
- **FR-022**: グラフで表現される情報は、表形式やテキスト要約など非視覚的な手段でも同等に取得できなければならない。
- **FR-023**: 記録が0件の画面は、記録がないことを分かりやすく示し、記録の作成へ導く表示をしなければならない。

### Key Entities *(include if feature involves data)*

- **体重記録**: 記録日と体重(kg)を持つ。日々の体重推移の基礎データであり、消費カロリー算出にも用いる。
- **トレーニングセッション**: 記録日・実施時間(分)・強度区分を持つ。複数の種目記録を含む。
- **種目記録**: トレーニングセッションに紐づき、種目・セット数・回数・重量を持つ。
- **種目マスタ**: 種目名・METs値・出典を持つ固定データ。種目記録から参照される。
- **歩数記録**: 記録日と歩数を持つ。
- **食材**: 食材名・100gあたりカロリー・タンパク質・脂質・炭水化物を持つ参照専用の固定データ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 開発者は体重記録の新規作成を1分以内に完了できる。
- **SC-002**: 開発者は種目3件程度を含むトレーニングセッションの記録を3分以内に完了できる。
- **SC-003**: セッション詳細を開いてから3秒以内に、消費カロリーと算出根拠(計算式・定数・出典)が表示される。
- **SC-004**: 体重・トレーニングセッション・歩数のすべての入力フォームについて、キーボードのみで入力から保存までの操作を完了できる。
- **SC-005**: すべてのグラフ表示について、同じ情報を表形式またはテキスト要約でも取得できる。
- **SC-006**: 不正な値を入力した場合、対象フィールドに関連付けたエラーメッセージが表示され、修正後に保存が成功する。
- **SC-007**: 直近30日分の体重・トレーニング・歩数の記録がある状態で、日次・週次・月次いずれの集計表示も5秒以内に表示される。

## Assumptions

- 永続化の具体的な実装(ローカル完結かサーバー同期かを含む)は `/speckit-plan` で決定する。本specでは、憲法の原則VIに従い、データ層を差し替え可能な抽象の裏に置くことのみを前提とする。
- 集計に用いるタイムゾーンはJST固定とする(単一ユーザー・単一環境のため、タイムゾーン切り替えは考慮しない)。
- 各数値の入力可能範囲・小数点以下の桁数は、実装時にZodスキーマとして定義する初期値として以下を想定する: 体重 20.0〜300.0kg(小数点第1位)、実施時間 1〜600分(整数)、強度区分は3段階の区分値、セット数1〜20(整数)、回数1〜100(整数)、重量0〜500kg(0.5kg刻み)、歩数0〜100,000歩(整数)。
- 消費カロリーは、トレーニング・歩行それぞれのMETs方式による推定消費エネルギーの合算とし、安静時代謝(BMR)を別途加算しない。これにより「総消費」と「活動による増分」の二重計上を避ける。
- 記録が0件の画面では、空状態メッセージと記録作成への導線を表示する。
- 種目マスタ・食材一覧は初期セットとしてアプリに同梱される固定データとし、具体的な件数・内容は実装時に定める。
- 週次・月次集計は月曜始まりとし、「今週」「今月」は期間開始日から当日までの経過分のみを対象とする。
- 同一日付への記録はすべて上書きとし、1日1件に統一する(トレーニングセッションを含む)。
