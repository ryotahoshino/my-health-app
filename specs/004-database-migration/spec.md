# Feature Specification: 記録データの保存先をマネージドデータベースへ移す

**Feature Branch**: `004-database-migration`

**Created**: 2026-10-13

**Status**: Draft

**Input**: 記録データの保存先を、開発用PCのローカルファイル(SQLite)から、無料枠で使えるマネージドデータベース(Neon)へ移す。テストとローカル開発はプロセス内で動くPostgres(PGlite)を使う。スキーマの変更はSQLファイルによるマイグレーションとして管理し、アプリ起動時のスキーマ作成をやめる。既存のローカル記録は移送する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 記録が開発用PCの外に保存される (Priority: P1)

記録(体重・トレーニング・歩数)が開発用PCのファイルではなく、ネットワーク越しのデータベースに保存される。
利用者から見た画面の操作と結果は移行前と変わらないが、記録は特定の1台のPCに縛られなくなる。

**Why this priority**: 以降のすべての作業(公開、LLMを使う機能)がこの土台を前提にする。
ローカルファイル前提のまま機能を積み増すと、後からの載せ替え範囲が広がり続ける。

**Independent Test**: 新しい保存先に接続した状態で4画面(体重・トレーニング・歩数・食材)を開き、
記録の作成・取得・削除・期間切替が移行前と同じ結果になることを確認する。

**Acceptance Scenarios**:

1. **Given** 新しい保存先が空の状態、**When** 体重を記録する、**Then** 一覧に表示され、再読込後も残っている
2. **Given** 同じ日付の体重記録が既にある、**When** 同じ日付で記録する、**Then** 新規作成ではなく上書きになる
3. **Given** 種目を含むトレーニングのセッションがある、**When** そのセッションを削除する、**Then** セッションと種目内訳の両方が消える
4. **Given** 複数日の記録がある、**When** 週次・月次に切り替える、**Then** 移行前と同じ集計結果が表示される
5. **Given** 保存先の接続情報が未設定または誤っている、**When** サーバーを起動する、**Then** 原因が分かるメッセージで起動に失敗する

---

### User Story 2 - スキーマの変更が履歴として管理される (Priority: P1)

テーブルの追加・変更が、番号付きの変更単位として記録され、未適用のものだけが順に適用される。
アプリの起動時にスキーマを作る処理はなくなる。

**Why this priority**: 今後の機能追加(LLMの生成結果の保存など)で必ずテーブルが増える。
起動のたびにスキーマを作る方式は、共有のデータベースに対しては安全に使えない。

**Independent Test**: 空のデータベースに対して適用処理を実行し、必要なテーブルがすべて揃うこと、
同じ処理を2回実行しても失敗しないことを確認する。

**Acceptance Scenarios**:

1. **Given** 空のデータベース、**When** 適用処理を実行する、**Then** すべてのテーブルと制約が作られる
2. **Given** すべて適用済みのデータベース、**When** 同じ処理を再実行する、**Then** 何も変更されず正常終了する
3. **Given** 新しい変更単位を1つ追加した状態、**When** 適用処理を実行する、**Then** その1つだけが適用される
4. **Given** 適用処理を実行していないデータベース、**When** サーバーを起動する、**Then** スキーマは作られない(起動とスキーマ作成が分離されている)

---

### User Story 3 - 既存の記録が失われない (Priority: P2)

移行前にローカルに蓄積されている記録が、新しい保存先に移される。

**Why this priority**: 記録アプリとして、過去の記録が消えることは機能の価値を損なう。
ただし移行作業そのものは1回限りで、継続的に使う機能ではないため P1 より下げる。

**Independent Test**: 現行のローカルデータから書き出し、新しい保存先に取り込んだうえで、
記録の件数と内容が移送前と一致することを確認する。

**Acceptance Scenarios**:

1. **Given** ローカルに記録がある状態、**When** 書き出しと取り込みを行う、**Then** 記録の件数と内容が一致する
2. **Given** 一度取り込みを終えた状態、**When** 同じ取り込みを再実行する、**Then** 記録が二重に増えない
3. **Given** 固定データ(種目マスタ・食材)、**When** 取り込みを行う、**Then** 重複せず1組だけ存在する

---

### User Story 4 - 外部サービスに接続せずに検証・開発ができる (Priority: P2)

自動テストとローカル開発が、ネットワーク越しのサービスに接続せずに動く。

**Why this priority**: テストが外部サービスに依存すると、実行が遅くなり、ネットワークの状態で結果が揺れる。
憲法 原則III(テスト先行)と原則V(フェイクの依存を注入して検証)を維持するための条件になる。

**Independent Test**: ネットワークを切断した状態で、クライアントとサーバーの全テストが成功することを確認する。

**Acceptance Scenarios**:

1. **Given** ネットワークに接続していない環境、**When** 全テストを実行する、**Then** すべて成功する
2. **Given** 複数のテストが同じテーブルを使う、**When** 並行して実行する、**Then** 互いのデータに影響されない
3. **Given** ネットワークに接続していない環境、**When** ローカルで開発サーバーを起動する、**Then** 記録の作成と取得ができる

---

### Edge Cases

- 保存先への接続が一時的に失敗したとき、画面はどう振る舞うか(本specでは現状の振る舞いを維持し、
  専用のエラー表示は別specとする)
- 保存先が休止状態から復帰する際に応答が数秒かかるとき、読み込み中の表示が継続して出るか
- 適用処理の途中で失敗したとき、中途半端な状態が残らないか(1つの変更単位は全体が適用されるか、
  されないかのどちらかになる)
- 小数の扱いが変わることで、体重や消費カロリーの表示が移行前と変わらないか
- 同一日付への記録が、並行して2回送られたときに1件に収まるか
- 既存データの移送中に、現行のローカルデータを誤って書き換えないか(読み取りのみで行う)

## Requirements *(mandatory)*

### Functional Requirements

**保存先の移行**

- **FR-001**: 記録(体重・トレーニング・種目内訳・歩数)と固定データ(種目マスタ・食材)の保存先を、
  アプリのプロセス外にあるマネージドなデータベースにする
- **FR-002**: 4画面の既存の振る舞い(取得・作成・上書き・削除・期間集計)を変えない
- **FR-003**: 日付ごとに1件という一意性(同じ日付への保存は上書き)を維持する
- **FR-004**: トレーニングのセッションを削除したとき、その種目内訳も一緒に削除される
- **FR-005**: 日付は `YYYY-MM-DD` の文字列として保持し、期間集計のドメインロジックを変更しない
- **FR-006**: データベースへのアクセスはデータ層に閉じ、GraphQL の公開契約(クエリ・ミューテーションの形)を変えない
- **FR-007**: 取得に失敗したときの画面の振る舞いは現状を維持する(専用のエラー表示は本specの範囲外)

**スキーマの変更管理**

- **FR-008**: スキーマの変更を番号付きの変更単位として管理し、未適用のものだけを順に適用する
- **FR-009**: 適用済みの変更単位を記録し、同じ適用処理を繰り返しても結果が変わらないようにする
- **FR-010**: アプリの起動処理ではスキーマを作成・変更しない
- **FR-011**: 固定データ(種目マスタ・食材)の投入は、何回実行しても重複しない

**接続と秘匿情報**

- **FR-012**: 接続情報をコードおよびリポジトリ内の設定ファイルに書かない。ローカルは環境変数ファイル、
  CI は Secrets で渡す(憲法 原則VIII)
- **FR-013**: 接続情報が未設定または不正な場合、起動時に原因の分かるメッセージで失敗する
- **FR-014**: 保存先は環境ごとに差し替えられる(本番・ローカル開発・テストで別の保存先を指定できる)

**既存データの移送**

- **FR-015**: 現行のローカルデータから記録を書き出し、新しい保存先に取り込める
- **FR-016**: 取り込みは繰り返し実行しても記録が重複しない
- **FR-017**: 移送は現行のローカルデータを読み取るだけで、書き換えない

**検証**

- **FR-018**: 自動テストは外部のネットワークサービスに接続せずに実行できる
- **FR-019**: 各テストは他のテストのデータに影響されない独立した状態で実行できる
- **FR-020**: ローカル開発もネットワーク接続なしで動かせる

### Key Entities

- **記録**: 体重記録(日付・体重)、トレーニングのセッション(日付・実施時間・強度)、
  種目内訳(セッションに属する、種目・セット数・回数・重量)、歩数記録(日付・歩数)。
  いずれも日付が利用者から見た識別子になる
- **固定データ**: 種目マスタ(名称・METs・出典)、食材(名称・100gあたりのカロリー・PFC)。
  アプリが投入し、利用者は編集しない
- **スキーマの変更単位**: 適用順を持つスキーマ変更の1単位と、その適用済み記録

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 移行後、クライアントとサーバーの既存の自動テストがすべて成功する(移行前と同じ件数以上)
- **SC-002**: 既存データの移送後、記録の件数と内容が移送前と一致する(差分0件)
- **SC-003**: 空のデータベースに対して1回の適用処理でスキーマが揃う(手作業のSQL実行が0回)
- **SC-004**: 同じ適用処理を2回続けて実行しても失敗しない
- **SC-005**: ネットワークに接続していない環境で全テストが成功する
- **SC-006**: テストの実行時間が移行前の2倍以内に収まる
- **SC-007**: 接続情報が誤っている場合、起動から10秒以内に原因の分かるメッセージで停止する
- **SC-008**: リポジトリに接続情報・認証情報が含まれていない(検査して0件)
- **SC-009**: 個人利用の想定(1日あたり数十回の読み書き)で、保存先の無料枠の範囲に収まる
- **SC-010**: 移行後、4画面を通しで操作して(記録・一覧・削除・期間切替)、移行前と同じ結果が得られる

## Assumptions

- **保存先の選定**: 本番の保存先は Neon(無料枠のマネージド Postgres)、テストとローカル開発は
  プロセス内で動く Postgres(PGlite)を使う。会話での合意事項。無料枠の条件(容量・休止・復帰時間)は
  実装時に公式ドキュメントで確認する
- **ORM を導入しない**: 001 の research #2 で決めた方針を維持する。スキーマの変更管理は
  SQL ファイルと小さな適用処理で行い、マイグレーションフレームワークは導入しない
- **サーバーの公開は範囲外**: 本specの完了後もサーバーはローカルで実行する。ホスティング・独自ドメイン・
  アクセス制限(認証)は別specで扱う
- **単一利用者**: 複数ユーザー・共有機能は憲法の非目標。利用者ごとのデータ分離は考えない
- **既存データ**: 対象は開発者本人の記録のみ。移送の前にローカルデータのファイルコピーを取る
- **ドメインロジックは変更しない**: カロリー算出・期間集計の計算は本specの範囲外。
  日付を文字列として保持するのはこのため
- **GraphQL スキーマは変更しない**: クライアント側のクエリ・生成される型に変更が出ないことを前提とする
